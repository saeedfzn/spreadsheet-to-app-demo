3 · Automate the chasing

Power Automate flows

Four cloud flows on standard connectors (SharePoint, Approvals, Outlook and Teams) take the admin away. Below, the log shows each flow "running" as you use the app (simulated in this demo).

① New request → approver

When an item is created
  1. Look up the approver for the department; over £500 also goes to Finance.
  2. Start an approval the approver can action in Teams or Outlook.
  3. Write the decision and date back to the list.

② Decision → requester

When an item is modified (trigger condition: Status is Approved or Rejected)
  1. Email the requester the outcome and any comment.
  2. Approved items over £500: Finance is notified to raise the order.

③ Daily reminder

Scheduled, 08:00 weekdays
  1. Find requests pending more than 3 days.
  2. Send each approver one digest instead of many emails.

④ Monday summary

Scheduled, Mondays 07:00
  1. Last week's spend by department and anything overdue, posted to the managers' Teams channel.

5 · Power BI design

How the real Power BI report is built

Design notes for the report behind the dashboard above: model, measures and refresh. The measures below drive the four tiles.

Data model (star schema)

TableRole
RequestsFact table from the SharePoint list: one row per request (Cost, Status, Submitted, Decided).
DepartmentDimension from the Departments list (approver, budget). One-to-many to Requests.
CategoryDimension from the Categories list.
DateCalendar table marked as a date table, related to Requests[Submitted], for weekly and monthly trends.

Refresh & sharing

SharePoint Online List connector in Import mode, with scheduled refresh through the day. Published to a workspace, shared with managers and pinned as a tab in their Teams channel.

DAX measures

Approved Spend =
CALCULATE ( SUM ( Requests[Cost] ),
            Requests[Status] = "Approved" )

Pending Requests =
CALCULATE ( COUNTROWS ( Requests ),
            Requests[Status] = "Pending" )

Avg Days to Decide =
AVERAGEX (
    FILTER ( Requests, NOT ISBLANK ( Requests[Decided] ) ),
    DATEDIFF ( Requests[Submitted], Requests[Decided], DAY )
)

Overdue Requests =
CALCULATE ( COUNTROWS ( Requests ),
            Requests[Status] = "Pending",
            Requests[Submitted] < TODAY () - 3 )

7 · Keeping clear notes

Build notes for the real version

SharePoint Lists data model

ListKey columns
RequestsItem, Department (lookup), Category (lookup), Cost, Requester (person), Status (choice), Approver (person), Submitted, Decided
DepartmentsName, Approver (person), Budget
CategoriesName. (The £500 Finance threshold is one admin setting, not hard-coded.)

Indexed on Status and Submitted, with delegable filters, so the app stays correct as the list grows past Power Apps' data row limit (500 by default, 2,000 max).

How I'd deliver it

  1. Sit with the team and map how requests really flow today.
  2. Prototype in days, put it in front of users, change what they don't like.
  3. Test the edge cases: duplicates, no approver, over-limit spend, someone approving their own request.
  4. Permissions: requesters see their own items, approvers their department, admins everything.
  5. Hand over a short user guide and an admin guide so the team can run it without me.

Access, admin & licences

  • SharePoint groups: Requesters (add, and read their own items), Approvers and Owners. "Own items only" is set on the list itself, because filtering in the app alone isn't security.
  • Nobody can approve their own request: the flow checks requester ≠ approver.
  • Power Apps and Power Automate on standard connectors run on normal Microsoft 365 licences. Sharing the Power BI report needs Power BI Pro (or a capacity). Copilot Studio, AI Builder and Copilot in Power BI are paid extras, so they're costed before any pilot.
